# 📖 写给人看的文档

一套随开发过程执行的文档规则：让第一次来的人很快看懂项目用途，沿最短的默认路径得到第一个结果，并知道下一步去哪。
有没有 agent 都适用。human-readme 工作流（[`SKILL.md`](SKILL.md)）按这些规则一步一步做；下面的检查清单是简短版。

> **为什么需要它：** AI 能一次读完所有内容，所以 agent 写的 README 常把功能平铺堆在一起。人通常按标题扫读、挑一条路走，很难一次消化平铺的信息；用途写不清，读者就得花更多力气才能看懂。

## ✔️ 检查清单

- 动笔前：想清楚写给谁、他要完成什么、怎样算完成；不确定时写给第一次用的人。先找已经讲这件事的页面。
- 标题下面放一行小目录：链接每个 `##` 小节，用 ` · ` 隔开；对外的入口（比如可以安装的东西的目录）放在最后，加粗。
- 亮点：第一句说清谁用它解决什么问题，再给一个看得到的结果；读者会拿它和熟悉的东西比时，紧接着说清区别（要比的点多就加对照表），对方能做到的照实写。
- 安装并首次跑通：一条默认路径；前提写在需要它的那一步前；每种电脑一行，写明容易混的情况走哪一行；编号小步，一步一个动作，第一步写怎么打开终端；步骤里遇到的提问在那一步写一句，链接到最后的列表。安装方式不止一种时，先说清是二选一（“选哪种”的表，方式 A / 方式 B），不要写得像先后两步。
- 需要安装的工具，按这个顺序分节：系统要求、安装、每天怎么用，然后是案例，第一句说它展示什么、做出什么；用户的文件放在哪里，单独一页。
- 能做什么：几件常见的事，每件一行一个链接。常见问题：只收真实、反复出现的。
- 首页不放：完整参数表、详细的内部架构、开发历史、台账、agent 指令、还没交付的功能。每个事实只在一处维护。
- 子页面每页一种用途（入门教程、操作指南、参考、原理说明）。项目自己定义的指标单独一页。
- 每个 `##` 标题前加一个 emoji；按同几项比较的内容放表格；单元格里超过一个短句的拆成分点（`• a<br>• b`）。
- 交付前：照默认路径走一遍，写下在哪里验证、结果、哪些没验证；本地链接和锚点都能打开。

## 🧭 三条原则

1. **漏斗式：** 从“是什么、为什么”写到细节，读者在任何一层停下都有收获。主页只放最常走的路，细节用链接带出去。
2. **每个事实有一个维护源：** 命令、参数、版本要求各在一页维护。主页上的最小命令、摘要和双语版本可以重复，但改动时一起更新；完成某一步所需的前提要在这一步前直接写出，不要只留一个链接。
3. **以读者完成任务为准：** 好不好看的是读者能否看懂、跑通、找到下一步，而不是篇幅或章节齐不齐。

## 🏠 主页（README）的四段

下面是默认骨架，不是所有项目的固定版式：数据集、规范库这类项目，“安装”对应“获取和使用的最短路径”；已经成熟的主页，按读者任务判断要不要调整，不为套版式而重排。

| 顺序 | 段落 | 必须做到 | 不要 |
| --- | --- | --- | --- |
| 1 | **亮点** | • 第一句说清“谁用它解决什么问题”<br>• 读者很可能拿它和熟悉的东西比（例如平台自带的功能）时，紧接着用一句话说清区别；要比的点不止一个，就加一张两者在同几个点上的对照表；对方能做到的照实写<br>• 再给少量有依据的差异，和一个能看到结果的示例（截图、命令输出、输入输出对照均可） | 罗列全部功能；写无法验证的形容词；对明摆着的“它和 X 有什么区别”不回答，或者贬低 X |
| 2 | **安装并首次跑通** | 默认路径一条到底；安装方式不止一种时，先说清是二选一（“选哪种”的表，再分方式 A / 方式 B），不要写得像先后两步；前提（系统、账号、GPU、费用）写在对应步骤前；输入从哪里来要写清；最后给一个最小示例和“看到什么就算成功”<br>• 读者用的电脑不同时：按“哪种电脑”各给一行，并写明容易混的情况走哪一行（如 Windows 里的 WSL 仍用 Windows 安装包）<br>• 需要安装的东西：安装前单独一节系统要求，按“哪种电脑”各一行（系统版本；运行环境版本，如 Python 3.9 或更新；安装程序会自己装什么；它不装的东西怎么查看、怎么升级）；然后按这个顺序分成几节：安装（只写安装本身）、每天怎么用（怎么开始），最后是一个案例，标题就叫案例，开头一句写清它展示什么、做出什么（如“写下你做某件事的方法：它会变成一个可以运行的工作流”），引用“每天怎么用”里的步骤，不重复写<br>• 用户的文件放在哪里以及怎么从平常用的文件管理器找到（如 WSL 的家目录，不是 Windows 的硬盘）：单独写一页，从“能做什么”表格里的一行链过去，不在 README 里单独成节<br>• 步骤写成编号小步，一步一个动作；第一步写清怎么打开要输命令的终端（如 Windows：打开 PowerShell，输入 `wsl`）；读者不是非做不可的步骤（如练习文件夹）写明为什么要做<br>• 步骤里会遇到的提示（如 `Durweg 装在哪里？`）：在那一步只写一句怎么选，链接到 README 最后一节的列表，一项一行，每项附对应说明文档的链接 | 把每个平台的完整分支都摊在主页；只写到“安装完成”为止；一段里塞好几个动作 |
| 3 | **能做什么** | 按读者要完成的任务列（“在另一台机器恢复配置”），每项一句话加链接；模块名可以作补充；只挑常用的，完整目录另开一页 | 只列内部模块名；在主页展开参数 |
| 4 | **常见问题** | 只收真实反复出现、又无法从主流程消除的问题，每条一句话加排障链接 | 为了凑章节编问题；用 FAQ 掩盖错误的安装步骤 |

末尾一行放“更多文档 · 求助 · 许可证”即可。某段还没有内容时，**不建空壳**。

**主页不放：** 完整参数表、详细的内部架构（一两句概览可以）、开发历史、实验台账、agent 指令、尚未交付的功能。

## 📂 子文档：按用途分开写

主页链接出去的页面，每页只承担一种用途（来自 [Diátaxis](https://diataxis.fr/)）：

| 用途 | 读者在想 | 例子 |
| --- | --- | --- |
| 入门教程 | “带我走一遍” | 从零跑通第一个完整例子 |
| 操作指南 | “我要做成某件事” | 迁移到新机器、接入 GPU 服务器 |
| 参考 | “这个参数是什么” | 配置项表、命令行选项 |
| 原理说明 | “为什么这样设计” | 架构、取舍、限制 |

不必一开始就建四个目录。小项目一个 README 加几页操作指南就够，内容长了再细分。混写是最常见的问题：操作步骤里插大段原理时，把原理移到单独一页，留一个链接。

### 项目自定义的指标和公式

项目自己定义的指标或公式（不是 MAE、准确率这类通用常识）要有一页专门说明，例如 `docs/metrics.md`。它属于参考和原理说明，放在子文档里；主页"能做什么"里留一行链接。自己造的数字，读者会忘记它是什么意思，一个月后的作者本人也一样。

- **开头放对照表**："想知道什么 → 看哪个指标"，每行链接到对应小节。
- **先讲记号和区域**：每个记号只定义一次。指标涉及区域、mask 或其他空间记号时，配一张示意图。
- **每个指标按顺序写**：
  - **回答什么问题**：一句话。
  - **公式**：和代码的算法完全一致。
  - **数值怎么读**：0、1、大于 1、负数各表示什么；什么情况下不可计算（如区域为空、分母为 0）。
  - **判据**：有的话，写算作成功的阈值。
  - **实际结果**：典型数值及出处（运行名、表格）。
  - **实现位置**：函数和文件，带链接。


## 📋 标题和表格

README 每个 `##` 节的标题前加一个提示内容的 emoji（如 💻 系统要求、🧭 安装、📅 每天怎么用、🚀 案例、🙋 我想……、🛠️ 常见问题），读者扫一眼就能找到要看的那一节。按同样几项比较多个对象的内容（每种电脑、每个文件、每件想做的事、每个提问一行）写成表格；要按顺序做的步骤仍写成编号列表。页内链接要指向带前导连字符的锚点（如 `#-案例写下你的方法`）。

### 标题下面的一行小目录

标题正下方放一行，按顺序链接 README 的每个 `##` 小节，用 ` · ` 隔开，用和标题一样的 emoji，读者一眼就能看到整页有什么，并直接跳到要看的部分。很多读者会找的、README 以外的入口（比如可以安装的工作流目录）放在最后，加粗。只列 `##` 一级，这样目录保持一行。例子：[Durweg 的 README](https://github.com/musetee/durweg/blob/main/README_cn.md)。

### 表格里的说明

表格单元格里的说明超过一个短句时，拆成分点，每点一行，免得表格太宽、难读。GitHub 的表格里放不了 Markdown 列表，写成 `• 第一点<br>• 第二点`。内容不删：拆开，不砍掉。只有一个短句的单元格保持原样。例子：[Durweg 的 README](https://github.com/musetee/durweg/blob/main/README_cn.md) 里的表格。

## 🔄 随开发过程执行

| 时机 | 做什么 |
| --- | --- |
| **动笔前** | 想清楚这次写给谁、他要完成什么、怎样算完成；先找现有页面，确定这件事在哪页维护。不确定读者时，默认写给第一次用这个项目的人。 |
| **项目初建** | 写亮点和“安装并首次跑通”，加一行继续阅读的入口。 |
| **加功能** | 先问：读者能做的事变了吗？新用户需要发现它，才在主页“能做什么”加一行；操作细节写进对应操作指南，参数写进参考。不必每个功能一页。 |
| **修问题** | 先修原来的步骤。修不掉、又反复出现的，才进排障页或 FAQ。 |
| **发布或移除** | 核对示例和当前版本一致；删掉指向已移除功能的入口；有破坏性变化时给迁移说明的链接。 |

## ✅ 交付前自检

1. 照着默认路径从前提走到成功结果；写下在什么环境验证过、结果是什么、哪些没验证。“命令看起来对”不算验证。
2. 本地链接和锚点都能打开。
3. 回答四个问题：读者在第一屏能说出项目用途吗？能选出默认路径吗？能认出成功了吗？知道下一步去哪吗？

| 检查 | 方式 |
| --- | --- |
| 本地链接、锚点、Markdown 格式；必需内容（用途、默认开始路径）在不在 | 自动检查，失败就修 |
| 默认示例能否跑通 | 能自动跑就跑；需要账号、硬件、付费时写明验证边界 |
| 篇幅变长、段落过长、标题过深、外链暂时打不开 | 只提示，由人判断 |
| 读者能否看懂、跑通 | 首次建立或明显改动入门路径时，条件允许就找一个没参与开发的人按任务试读；agent 模拟只作补充。平时的小改做上面的自检即可 |

篇幅不设硬上限：硬性字数或命令块数会诱导把多步挤进一个大代码块，反而难执行。具体耗时也不作通用承诺，需要时按前提实测后再写。

## ✏️ 规则本身怎么改

这些规则会随实际使用调整。写真实 README 时发现规则不合适，或者你提出了新要求：先在当前项目里按你的要求改，再决定要不要把它变成通用规则（工作流第 7 步会问）。要的话，本页和英文版 [`guide.md`](guide.md) 一起改，在工作流的 [`CHANGELOG.md`](../../CHANGELOG.md) 里写明原因，然后推送。

- 你的方法库指向的是你自己的这份仓库（`durweg library list` 能看到文件夹）时，改完马上生效。
- 从目录里安装这个工作流的人，运行 `durweg update`（或 `durweg library update human-readme`）就会拿到新规则。
- 已经开始的运行，继续用开始时的规则：每次运行开始时都会复制一份工作流。

## 🔍 对照示例

下面的 MyTool 是虚构的，命令、链接和输出只用来示意结构。

**不好**（功能平铺，读者读完不知道从哪开始）：

````markdown
# MyTool
MyTool 支持 A、B、C、D、E、F 功能，包含 core、io、cli、plugin、remote 五个模块，
配置项有 --foo --bar --baz ……（完整参数表 60 行）
## 安装
pip / conda / docker / 源码 四种方式……（每种 15 行）
## 架构
……
````

**好**（四段，细节链接出去）：

````markdown
# MyTool
把医学图像的分割结果转成可编辑的 3D 网格，给做手术规划的医生和工程师用。
![输入 → 输出对照图](docs/img/demo.png)

## 安装并首次跑通
需要 Python 3.10+ 和 git。

```bash
git clone https://github.com/you/mytool.git && cd mytool
pip install .
mytool convert examples/liver.nii.gz -o liver.stl
```

看到 `Saved liver.stl (12,345 faces)` 即成功。其他安装方式见[安装指南](docs/install.md)。

## 能做什么
- 一次转换整个文件夹 → [批量转换](docs/batch.md)
- 导出 OBJ 并保留标签颜色 → [导出格式](docs/export.md)
- [全部功能与参数](docs/reference.md)

## 常见问题
- 报 `Unsupported file format`：[排障](docs/troubleshooting.md#formats)

[更多文档](docs/) · [提问](https://github.com/you/mytool/issues) · MIT
````
