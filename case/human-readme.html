Durweg case

A README for people (the aiagents-public way)

Made with Durweg on 2026-10-31. Workflow: human-readme.

The method

Task

Write a project's README (the front page, for people) the way aiagents-public does it: someone who comes for the first time sees on the first screen what problem the project solves, picks the one way to install for their computer, knows how to use it every day and where their files are, gets an example working, and knows where to go next.

How I do it

  • Find the core: one sentence with the project's core value and the problem it solves, as the README's first sentence; no story, no list of features
  • Pick the reader and the default path: write for a first-time user by default; one install line per kind of computer, saying which line the easily confused cases take (e.g. WSL on Windows uses the Windows installer)
  • Build the front page, each part its own section: install (only installing) → every day (numbered small steps, the first says how to open the terminal) → where the files are and how to find them → example (its first sentence says what it shows and makes, and it refers to the daily steps) → I want to … (one task per line, with a link) → the list of explanations at the end
  • Move details off the front page: step-by-step install, special regions, uninstall, full option and command tables each get their own page (in Chinese and English); the front page keeps one sentence and a link
  • Walk it once for real: on a new computer or a new WSL, follow the front page from the start until the example succeeds; write down where it was verified, the result and what was not verified
  • The user reads it with a beginner's eyes and gives comments one by one
  • Change this project's README by the comments, Chinese and English together, one thing at a time
  • After each comment is done, ask the user whether it should become a general rule; if yes, update the human-docs rules (Chinese, English and the short version) and write the reason in the CHANGELOG
  • Repeat "walk it → read → change" until the user is happy

Where it goes wrong

  • The first sentence tells a story or lists features, so you cannot see what problem it solves
  • WSL users take the Linux line as theirs
  • Beginners do not know how to get into a terminal or into WSL
  • One paragraph holds several actions and is hard to read
  • Install, everyday use, where projects live and the trial are mixed in one section
  • A prompt that appears during a step (e.g. Codex's "hooks are new or changed") is not explained and scares beginners
  • Screenshots nobody understands
  • Table cells that are too long
  • Saying it works without walking it once
  • The Chinese and English versions drift apart

Where I decide

  • How the first sentence (the core value) is worded
  • Whether I am happy with the README after each round
  • Whether a new requirement of mine becomes a general rule

Lessons

  • The README's first sentence tells no story; it only says the project's core value and the problem it solves.
  • Always read it with a beginner's eyes when it is written: where reading stops, change that, one thing at a time.
  • Each section heading gets an emoji; content comparing items on the same points goes in a table, steps done in order in a numbered list.
  • Only real use shows what is missing: for example, after installing Codex first and Claude later, you do not know whether Claude can use Durweg; questions like this go into the common problems.
  • After each new requirement is done, ask: should this become a general rule for every project from now on?

Durweg 案例

写给人看的 README（照 aiagents-public 的做法）

用 Durweg 制作于 2026-10-31。工作流：human-readme。

方法

任务

给一个项目写 README（写给人看的首页），做到 aiagents-public 那样：第一次来的人在第一屏看懂项目解决什么问题，按自己的电脑选一条路装好，知道每天怎么用、文件在哪，跑通一个案例，并知道下一步去哪。

我怎么做

  • 定核心：用一句话写出项目的核心价值和它解决的问题，作为 README 第一句；不讲故事，不罗列功能
  • 定读者和默认路径：默认写给第一次用的人；按电脑种类各给一行安装入口，写明容易混的情况走哪一行（如 Windows 里的 WSL 用 Windows 安装包）
  • 搭首页骨架，各自成节：安装（只写安装）→ 每天怎么用（编号小步，第一步写怎么打开终端）→ 文件放在哪里、怎么找到 → 案例（第一句说它展示什么、做出什么，引用每天的步骤）→ 我想……（一行一个任务加链接）→ 末尾的说明列表
  • 把细节移出首页：分步安装指南、特殊地区、卸载、参数和命令全表各放一页（中英两版），首页只留一句加链接
  • 实际走一遍：在新电脑或新 WSL 上照着首页从头做到案例成功，记下在哪里验证过、结果、哪些没验证
  • 用户以新手的眼光读，一条一条提意见
  • 按意见改这个项目的 README，中英文一起改，一次只改一件事
  • 每条意见改完后问用户：要不要变成通用规则；要的话更新 human-docs 规则（中英文和精简版）并在 CHANGELOG 写明原因
  • 重复“走一遍 → 读 → 改”，直到用户满意

容易出错的地方

  • 第一句讲故事或罗列功能，看不出解决什么问题
  • WSL 用户把 Linux 那一行当成自己的
  • 新手不知道怎么进入终端或 WSL
  • 一段话里塞好几个动作，读不下去
  • 安装、每天怎么用、项目放在哪、试用混在一节里
  • 步骤里冒出的提示（如 Codex 的 “hooks are new or changed”）没解释，把新手吓住
  • 截图看不懂
  • 表格单元格太长
  • 没实际走一遍就说能跑通
  • 中文版和英文版不同步

由我拍板的地方

  • 第一句（核心价值）怎么写
  • 每一轮改完的 README 我是否满意
  • 我提的新要求要不要变成通用规则

经验

  • README 第一句不讲故事，只说项目的核心价值、解决什么问题。
  • 写完一定要用新手的眼光读一遍：哪里读不下去，就改哪里，一次只改一件事。
  • 每节标题加 emoji；同样几项要比较的内容用表格，按顺序做的步骤用编号列表。
  • 真实用过才知道缺什么：比如先装 Codex、后装 Claude，就不知道 Claude 能不能用 Durweg，这种问题要写进常见问题。
  • 每条新要求改完都问一句：要不要变成以后所有项目的通用规则。
